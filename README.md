# 商场餐饮排队热区分群

长河广场三层餐饮运营组管理 7 个堂食和快闪入口。午高峰时，巡场人员以前用纸面时点表记录队尾，运营领班截取楼层图在群里圈热区，现场人员再用对讲机确认到场。缺测和零排队容易混淆，孤立长队会被误判为连片拥堵，群里的指令也很难核对是否有人认领和复测。

本项目将巡场计数、同层空间密度判断、楼层运营确认和现场复测串在一起。上游是门店入口坐标和人工计数，下游是现场疏导、临时控流、门店恢复工单和交班简报。

## 启动

```sh
cp .env.example .env
docker compose up -d --build --wait
```

访问 `http://127.0.0.1:18251`。FastAPI 文档在 `http://127.0.0.1:19251/docs`，MySQL 本机端口为 `17751`。默认自动执行幂等 seed，也可手动执行 `docker compose exec -T backend python -m scripts.seed_demo`。停止使用 `docker compose down`，需要清空演示数据时使用 `docker compose down -v --remove-orphans`。

| 演示账号 | 角色 | 工作页面和操作 |
|---|---|---|
| `patrol` | `observer` 巡场采样 | 选择门店和窗口，提交排队人数，按补采清单补录 |
| `floorlead` | `operator` 楼层运营 | 登记门店、下发补采、封存热区、分配等候线、安排控流、立单和核准服务恢复、发布交接简报 |
| `guide` | `steward` 现场疏导 | 认领疏导单，登记入线及释放，执行控流并复测解除，记录门店措施和后续复查，完成疏导和签收简报 |

三个演示账号的口令都是 `changhe-demo`。三个角色可读全部业务页面，写操作按岗位授权。账号只用于本地演示。

## 午高峰演示

1. 打开 2026 年 11 月 21 日的三层 12:00 观测。门店档案里，禾野煲仔位于 `(31,24)`，疏导点为东廊 E2 黄线。
2. 巡场查看 `12:00` 和 `12:15` 的晴茶快闪记录，实测 20 和 22 人。
3. 复核 `12:30`、`12:45` 两处缺测。空格为待采，零人记录显示为 `0`。
4. 楼层运营打开热区工作台，从 13:00 汇总这批观测并封存，等待 worker。
5. 刷新结果可看到三枚核心点和小满甜品边界点。桥边烤肉显示为孤立噪声点，晴茶快闪只列在样本不足栏。
6. 运营确认热区后，系统以首选锚点禾野煲仔的东廊 E2 黄线创建疏导任务。
7. `guide` 认领任务。13:05 复测 11 人时结案会被拒绝。
8. 13:12 再次测得 4 人，填写“东廊队尾回到等候线内”，任务进入已结案。

## 午高峰扩展流程

1. 选定 3F 的 12:00 楼层小时。楼层运营在「缺测补采」为只有两个观测窗口的晴茶快闪下发任务。巡场通过任务跳至采样矩阵，直接定位 12:30 缺测位置并录入 17 人。零人也算实测；第三个有效窗口自动完成补采。无法补采时，运营填写豁免原因。已经下发的待补采任务会阻止封存。
2. 封存小时并确认热区后，从「客流疏导」进入「等候线容量排班」。运营可登记同层等候线，例如东廊 E2 北侧临时线容量 12 人。为疏导单预留 13:00 时段的 8 个名额。现场疏导员认领后登记实际入线 5 人，通道恢复后释放名额，再按复测人数提交结案。等候线按 15 分钟计容，同层同一时段可以共享名额。可预留时段为观测小时结束后的两小时。未使用的预留可由运营取消后重新安排。
3. 所有热区确认且疏导结案后，楼层运营从「高峰交接简报」发布该小时的冻结快照。交班时可核对封存观测覆盖、复测人数、实际入线和仍需关注的样本不足及孤立拥堵入口。现场疏导员填写下一巡安排并签收，补采豁免原因随简报保存。

补采状态 `open / complete / waived` 见 `002_floor_operations.sql`、`coverage.py`、`coverage.js`。排班状态 `booked / in_use / released / cancelled` 见 `002_floor_operations.sql`、`lanes.py`、`lanes.js`。简报通过发布与签收字段区分状态，见 `handoffs.py`、`handoffs.js`。扩展 API 路由在 `extension_routes.py`，入参在 `extension_contracts.py`。旧数据卷启动时自动执行加表迁移，无需清空原观测数据。

## 临时控流与服务恢复演示

1. 用 seed 的三层 `2026-11-21 12:00` 封存观测后确认热区。锚点禾野煲仔的封存中位数为 22 人。现场疏导员领单后可从该任务直接打开同一小时的「临时控流」。
2. 楼层运营按现场队尾 34 人下发「取餐错峰叫号」。起报门槛取 25 人和「封存中位数加 5 后向上取整」两者中的较高值。每张疏导单同一时间只允许一个待执行或执行中的方案。
3. 认领原疏导单的人启动方案。若尚未启动，运营可填写原因撤销。执行中复测 23 人时系统拒绝解除，降至 22 人及以下可解除。疏导结案仍须低于 8 人并释放原有等候线预留。
4. 运营在「服务恢复」为禾野煲仔建立工单，并引用已解除的控流方案。封存图显示的孤立长队桥边烤肉也可直接立单。同门店同小时一张工单。
5. 现场人员在 `13:00` 登记“分开扫码与取餐队伍并增派一人”。`13:15` 复查为 5 人，`13:30` 复查为 3 人。复查从措施后至少 15 分钟开始，按 15 分钟窗口追加，保留人数、现场说明和记录人。
6. 最近两条须是连续窗口且均少于 8 人，运营方可结案。缺窗或回升至 8 人会推迟结案。疏导结束后可发布交接简报，其中交接当时仍在跟进的工单可由接班人继续处理，已发布快照保留当时状态。

控流状态 `planned / active / resolved / cancelled` 定义于 `003_surge_response.sql`，规则见 `surge.py`、`surge_policy.py`，显示见 `surges.js` 与 `handoffs.js`。恢复状态 `open / monitoring / closed` 定义于 `004_tenant_recovery.sql`，规则见 `recovery.py`、`recovery_checks.py`，显示见 `recoveries.js`、`recovery-evidence.js` 与 `handoffs.js`。`peak_routes.py` 和 `peak_contracts.py` 提供 API 与输入校验。控流方式 `meter_entry / stagger_pickup` 在迁移、`SurgePlan` 和 `surges.js` 中定义。

## DBSCAN 口径

固定观察单位是一个楼层小时，最多 4 个按 15 分钟对齐的窗口。门店至少要有 3 个观测，且排队人数中位数达到 8 人，才参与 DBSCAN。以同层排队入口的米制坐标计算欧氏距离，`eps=18m`、`minPts=3`，邻居计入自身。核心点可以扩展邻域，边界点加入群但不扩展，符合拥堵和样本门槛却未分入群的点为噪声。样本不足者只在排除清单中出现，达样本数但低于拥堵门槛者显示为低于阈值。门店编号排序确定边界点和编号归属，输出可复现。每个群以排队中位数最高的核心门店为锚点，同值按门店编号排序。分析失败时回滚输出，楼层运营可对同一份封存数据重试。

## 技术和目录

| 模块 | 实现 |
|---|---|
| 页面 | Nginx、原生 HTML/CSS 和 JavaScript ES modules |
| API | FastAPI、Pydantic、JWT、PyMySQL |
| 数据 | MySQL 8.0 存业务实体和审计；Redis 存短时 worker 心跳 |
| 分析 | 独立 Python worker 从 MySQL 队列取任务，事务内写热区、成员、锚点和运行状态 |

`backend/migrations/001_queue.sql` 定义数据库约束，`backend/src/shift.py` 实现采样和任务流转，`backend/src/density.py` 实现聚类，`backend/scripts/seed_demo.py` 管演示数据。`frontend/src/pages/` 包含九个业务视图，`ui.js` 定义共享组件和显示枚举，`state.js` 管 JWT 会话和请求。角色、点类型、任务状态见 `backend/src/contracts.py`、MySQL `ENUM` 和 `frontend/src/ui.js`。楼层小时状态见 `001_queue.sql`、`shift.py`、`worker.py` 和 `ui.js`。

`.env.example` 记录三个端口、数据库口令、JWT 密钥和 seed 开关。容器本地开发可修改源文件后执行 `docker compose up -d --build <service>`，也可在已启动的后端运行 `docker compose exec -T backend python -m scripts.seed_demo`。初始架构由 MySQL 在新卷启动时建立。扩展表由后端在启动时幂等创建。MySQL、Redis 和 worker 共享运行目录分别有命名卷。若本机有其他工程使用相同端口，可在 `.env` 中覆盖。
